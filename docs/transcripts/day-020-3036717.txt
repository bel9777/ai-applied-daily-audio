That guarantees only an actual human sitting at the console can approve the action—the model can't approve it for itself.
Alex: So how does Brian wire this up for his daily financial files?
Jordan: You add a pre-tool-use hook in your settings file. It listens for any tool that edits files, runs bash commands, or touches Box. Whenever Claude attempts one of those, the hook passes the payload to a small Python script on your local machine.
Alex: And what is that script looking for?
Jordan: It checks for keywords like upload, update, delete, or paths pointing to your journal upload directories. If it's a harmless read, it passes. If it spots a write, it halts and prompts for human approval. Even better, Brian can set an unattended environment variable for his scheduled background jobs. If that flag is on, the script doesn't bother asking—it denies the write automatically and logs the refusal to a local JSON audit file.
Alex: That sounds rock solid, but what's the catch? Where does this bite him?
Jordan: Two major traps. First, this gate does not give you segregation of duties by itself. If you write the prompt, run Claude, and click approve yourself, one person still controlled the whole pipeline. A controller will spot that instantly. To satisfy an auditor, you need a second approver's sign-off file in a directory you can't touch.
Alex: And if you can edit the audit log, it's not real audit evidence either.
Jordan: Spot on. That log has to be copied to write-once storage, and your hook settings need to sit under change management. Also, keyword matching is just a heuristic backstop—your primary line of defense still has to be your actual folder permissions and ERP access roles.
